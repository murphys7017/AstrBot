# OLV 实施细则：给执行模型的操作与验收说明

日期：2026-10-17。配套 [08 主任务书](08-olv-full-streaming-execution-plan.md) 与 [10 现场证据](10-olv-runtime-evidence-2026-10-17.md)。本文件描述目标行为，出现的伪代码和候选字段不是已经存在的 API；不得照抄后另造平行运行时。

**后续用户约束优先：**暂不改 Prompt 上下文结构，优先研究麦克风开始时提前准备。现有 Memory 是读已发布快照、后台独立更新，允许使用同作用域旧版本；详见 08 的 2.5。本文后续输入相关检索、revision 与缓存扩展不表示现有 Prompt 必须等待本轮记忆更新，也不授权将其改成同步召回。

## 1. 开始工作前的十条解释规则

1. “流式”必须写清 M0/M1/M2。动作 Provider stream=True 不代表主 Persona 或音频是 M2。
2. “首响”默认指输入确认到首个实际消费音频采样；另报用户松手到首采样。网络首 chunk、首字幕和完整回复完成分别计量。
3. 用户普通模式约三秒是需要尊重、匹配样本的体验观察，不是当前 M2 必须达到的已验证 SLA。
4. 正确性修复先做；架构优化按证据推进。全文详细不表示要求一次实现全文。
5. “低延迟”不允许丢失图像、记忆、动作或安全约束，也不允许减少回答内容后宣称同条件加速。
6. “尽早”指最早合法提交时点，不是未经确认的内容一到就播。
7. “有界等待”必须说明谁唤醒、失败怎么唤醒、取消怎么回收，不只是给 Queue 写 maxsize。
8. “状态独立”不代表身份独立；三条资源共享一个 Turn 和段身份，各自维护进度和终态。
9. “删除旧实现”只针对已经完成调用方迁移的内部路径；M0 是现有受支持模式，不能顺手删除。
10. 完成一批后继续用户已授权的后续任务；缺少现场环境时明确停在 source/boundary 级别，不靠追加 mock 抬高结论。

## 2. 第一批的具体操作顺序

### 步骤 A：建立不改行为的工作快照

- 读取两个仓库指南；记录 HEAD、工作区差异、相关文件是否有人正在修改。
- 只读核对部署副本、实际桌面构建和运行进程版本；无法确认时写 unknown。
- 读取 10 的两轮证据，重新搜索是否已有更新日志。不得假定最新源码等于进程加载代码。
- 列出当前环境能做的验证：静态、公开入口、loopback、真实 Provider、真实桌面/Live2D；不能访问的项注明原因。
- 输出一张简短工作表：R0–R8 的 exists/fixed/uncertain、证据、打算修改的入口。完成后开始必要实现，不等待无意义的额外批准。

### 步骤 B：先修入口身份 T0b

调用顺序必须追到：

```text
输入提交
  → Adapter _commit_inbound_message
  → message ID / frontend ID 记录
  → 平台事件交给 Core
  → PlatformTurnContextFactory.create / ensure_interaction_turn_state
  → 实际 Core Turn ID 成立
  → Persona header
  → event.open_interaction_incremental_output
  → Adapter.open_incremental_output
  → TurnCoordinator 校验映射和活动代次
  → OutputSegmentCoordinator 创建连接绑定 writer
```

填写身份表后再决定修复位置：

| 身份 | 唯一含义 | 不能替代它的值 |
| --- | --- | --- |
| capture stream ID | 一段麦克风传输会话 | 某个 VAD 子 Turn |
| frontend Turn ID | 桌面交互与回执归属 | Core UUID、协议事件 message_id |
| 输入 message ID | 输入消息身份 | 未经契约约定的 Core Turn ID |
| Core Turn ID | Core execution_scope/状态归属 | 随手取的当前活动 frontend ID |
| persona_result_id | 本次表达调用 | 整个连接或整个历史会话 |
| segment_message_id | 一段输出的稳定身份 | 每一帧新生成的信封 message_id |
| stream_id + seq | 某资源流及其顺序 | 另一资源的序号 |

优先复用已存在的可靠生命周期桥接。可选方案包括在 Core 接受入口身份后统一使用它，或在实际 Core 身份创建时绑定；不得同时做两个自动重绑入口。无论选哪种，需证明输入/VAD/主动输出/取消的现有消费者仍正确。

**此步不允许的修复：**删掉映射比较；把缺失映射当成功；遇到冲突就覆盖；将两个 ID 字段填为同一个值来绕过校验；仅修改测试注册顺序。

**可交付条件：**正常公开输入入口无需手填映射就打开 writer；旧 Turn/错误绑定仍被拒绝；真实日志至少能区分 M2 已选中与尚未确认。

### 步骤 C：修队列与 TTS 准入 T1

先画实际队列所有权，不要先添加更多任务：

| 队列/资源 | producer | consumer | 正常关闭 | 失败/取消关闭 |
| --- | --- | --- | --- | --- |
| PCM 文本输入 | Persona 可见增量 | 本 Turn PCM 服务 | 段 flush，最终输入 EOF | consumer 退出必须唤醒 producer |
| 旧完整段输出 | M0/M1 物化 producer | 对应 delivery task | 结束标记 | delivery 失败取消 producer |
| writer | Core/动作任务 | 同一连接 sender | 三条资源独立 end | 连接封闭，不重试已歧义发送 |
| motion Future | Adapter 动作任务 | 动作输出/结算 | 合法 payload 或空结果 | timeout/cancel 明确结果 |

M2 不得继续向旧完整段队列写入，哪怕短样本暂时没填满。

对“PCM consumer 已失败”的正确语义：

```text
文本已通过安全处理
  → 文本提交仍可进行
  → 检查本 Turn 音频支路状态
     running：有界提交，等待期间也观察 consumer 终态/Turn cancel
     failed：不再提交音频输入；已有音频前缀按失败规则排空/关闭
     cancelled：服从 Turn 取消，不继续生成可见内容
```

该伪代码只描述竞争关系。实际实现必须处理“检查 running 后 consumer 正好退出”的竞态：不能 check-then-put 后永久等待。若用 task race，结束后回收落败等待任务；若用 closable queue，需区分正常 EOF、失败与取消。

在取消路径禁止先等待向满队列写 sentinel 再取消消费者；不要 catch CancelledError 后吞掉取消继续跑网络任务。Provider/文本迭代器关闭应有有界清理并回收异常，不能泄漏悬挂 task。

use_tts 的决策只做一次并传给输出分支；false 时不创建 TTS 会话，音频资源按协议结束为空。TTS 不支持 PCM 的配置应在准入处明确选择允许的路径或报告音频不可用，不得在已有增量输出后偷偷切到完整音频重播。

### 步骤 D：修动作调度 T2

逐项审阅 scheduler 的判定顺序，先区分目标是“开启下一段”还是“给当前段添加动作”，再处理 blocker。

| 音频状态 | 动作状态 | 应有行为 |
| --- | --- | --- |
| 未起播但会有语音 | payload 已就绪 | 按语音同步契约等待首采样；不阻挡音频开始 |
| 本段音频运行中 | payload 就绪、尚未执行 | 允许本段 motion sink 加入，不被本段 audio blocker 拒绝 |
| 明确无音频 | payload 就绪 | 使用已有独立动作时间线，能结束和回执 |
| 音频起播前失败 | payload 就绪 | 按明确定义的降级行为执行或拒绝，不能永久 pending |
| 音频已结束 | 动作未就绪 | 仅在有界合法窗口等待；窗口外取消并记录过期 |
| 任意 | Turn 已打断/代次过期 | 禁止启动，回收任务/参数所有权 |
| 任意 | 资源已 terminal | 后续 payload 不能改写终态 |

修 R1 时不能仅把 `blockers.length` 判断删除；要防止上一段动作尾部与下一段动作互相覆盖。音频连续性与动作顺序若冲突，先明确各 sink 占用的参数和时钟，不能让一项改动隐式改变所有段的顺序语义。

动作任务创建时确定一个绝对 deadline；后续 context、gate、provider、parse、publish 使用 remaining，不逐阶段重新获得完整预算。配置和 Turn 剩余预算共同限制，不能再保留 0.75 秒或 Core 1 秒的隐性更短上限。

动作资源 end 和动作执行完成是两个事件：payload 已生产完成后仍可在时间线上执行；播放结束必须等实际 sink 结算。可选动作过期要释放引用，不把任务永远留到全局 shutdown。

### 步骤 E：首批检查与报告

使用实际 public boundary 做最小成功/拒绝检查，普通模式保留一个可比较的正常案例。不要把只修身份的批次顺便变成 AudioWorklet/ASR 协议迁移。

首批报告必须回答：真实入口 M2 是否可达；是否仍发生 fallback；TTS 关闭是否真的不请求；失败/取消是否回收；动作能否伴随音频；纯动作是否可结束；哪些结论只是源码证据。

## 3. 输出资源状态机与错误传播

以下状态是语义名称，复用现有字段映射即可，不要求添加同名类。

```text
production: absent/not_requested → open → completed | failed | cancelled
playback:   idle → preparing → playing → completed | failed | interrupted
```

资源选择“不请求”仍需满足当前协议的 start/end 或明确 absent 约定，不能让消费者无限等待缺失 stream。start 后必须且只能一次 terminal；重复终态是拒绝/去重问题，不是重新执行的许可。

| 事件 | 文本 | 音频 | 动作 | Turn |
| --- | --- | --- | --- | --- |
| PCM Provider 失败 | 若其余条件正常则继续 | 前缀保留，production failed | 仍可按自身期限完成 | 保留音频失败事实，不伪造全成功 |
| 动作 Provider 失败 | 继续 | 继续 | failed/expired | 有成功语音/文本时按现有可选动作政策结算 |
| Persona 后续格式失败 | 已提交前缀保留 | 不播未接受文本 | 不执行未校验记录 | incomplete/failed，明确原因 |
| 用户打断 | 停止新增提交 | 立即停止播放，禁止迟到追加 | 停止与释放控制权 | cancelled/interrupted 一次 |
| 连接失败 | 记录已知前缀 | 禁止转新连接重放 | 取消 | 由既有 owner 关闭 |
| 普通完成 | 文本生产完成 | EOF 后实际排空 | 已执行、明确 absent 或失败 | 满足全部结束条件后回执 |

不得只看一个 `success=True` 就覆盖另一支路已有失败。另一方面，不能把“可选动作没有 payload”无条件升级为语音失败。沿用现有契约，并明确纯动作段的区别。

## 4. 模式选择和发布边界

每次 Persona 调用固定一次模式，不能同一份内容同时 M1/M2 双发。建议诊断字段见下表；实际字段名可遵循现有日志风格。

| 字段 | 含义 |
| --- | --- |
| requested_mode | 用户设置与 Core 准入希望使用的模式 |
| selected_mode | 本次实际选择的 M0/M1/M2 |
| decision_reason | 正常选择、能力缺失、身份拒绝等明确原因 |
| published | 是否已有任何增量事件可能到达客户端 |
| config_revision / connection_generation | 设置快照和连接代次 |
| frontend_turn_id / core_turn_id | 不同身份域 |

既有降级仅能在未发布且契约允许时使用。writer 开始发送后网络错误具有歧义，不能根据本地 send 返回失败就断言客户端没收到；此时关闭并结算，禁止换路径重试。

同一 Turn 的 initial reply 和 delegated final 可能是不同 Persona invocation。不能把流式 active 标记跨调用保留，不能用前一次的 writer/结果 ID 给后一次发内容。现有 finally 清理和终态观察边界要保留。

协议扩展采用现有 handshake/capability 管理；若增加 credit 或动作 revision，先同时实现 producer/consumer 验证，再选择新模式。设置只是请求，不等于能力证明。不要引入自动“短句普通/长句流式”预测器；输出长度尚未知，新增预测可能增加一次模型等待。

## 5. T3 拆成可审阅的子任务

### T3.1 接收分发与播放等待分离

先明确消息的验证、入队、消费与副作用时点。入站完成严格校验和容量接纳后可以返回，PCM 在自己的 worker 顺序消费。文本/动作可独立前进，但仍属于同一有效 Turn。

前段音频 EOF 到达后可接纳后段有界 PCM，并不等于允许两段同时播放。playback worker 保持音频顺序；后段容量计入总上限，不能每段各自创建四秒无限叠加。

### T3.2 容量反馈契约

至少定义：连接代次、Turn/音频流身份、窗口单位、已接纳位置、可用容量/累计授予量、反馈频率、超时和取消处理。优先用单调累计值避免重复 ACK 扩大额度；确切协议在实现前写入 Live 契约文档。

发送方不得超过授予容量；接收方不得确认自己无法保存的数据；计数更新与实际所有权转移一致。容量反馈丢失可等待或失败，不能静默假定无限 credit。

### T3.3 死锁检查

检查以下等待环并证明已被打破：

- audio sender 持有 Turn 锁等待 credit，而 credit handler 需要同锁；
- PCM append 等播放排空，EOF 排在被阻塞的普通网络队列后；
- 取消排在满队列后，producer 又等取消才能退出；
- 所有消息槽被音频占满，控制/credit 无法进入；
- 客户端暂停消费时服务器继续把 Provider 全量结果存到内存。

允许为控制预留容量，但不能给任意未经身份校验的消息无限优先权。

### T3.4 停止条件

两端协议可跑通、队列有界、无上述等待环后才启用。若需要改变旧客户端公开协议但无法同步消费者，先交付已验证实现和清晰兼容边界，不强制上线。

## 6. T4/T5 的具体优化决策

### 6.1 提前准备而不盲目池化

先测 connect、task_ready、first_text、first_pcm、device_prepare。若连接和设备准备是关键路径，先做本 Turn 提前准备；只有证实服务商会话可安全复用时才加入池化。预热不能在 TTS 关闭或用户无此意图时无限发收费请求。

热连接状态至少包含 endpoint/credential identity/model/voice/proxy 及 idle/in_use/closing；敏感值不写日志。配置切换、鉴权失败、取消未确认和断线使相关会话失效。

### 6.2 输入前置等待

给 PTT 停止、截图、end 发送各自测量。根据结果选择最小方案：截图在用户说话期间提前采集并校验新鲜度；或者音频结束先触发 ASR，视觉材料另行绑定到同一输入且 Core 在必需图像就绪后才提交模型请求。

第二种方案改变输入契约，不能直接提前发送旧协议的 end 然后再补一个不被识别的图像。必须定义 input assembly 完成点和取消规则。用户明确问屏幕内容时图像不能降成 optional；普通知识问答的持续观察快照也不能未经产品定义自动删去。

### 6.3 能力摘要与提示词准备

现场存在 capability.schema 约 326 ms 的单次记录。先确认是否每轮都重复、是否由有效配置决定，以及为什么为 Persona 决策构造该范围能力。若可缓存，使用配置/插件注册/权限/Persona 版本键；权限变化需立即重新校验。

任务图拆分时列出每个 collector 的真正依赖和副作用；有插件共享 event mutation 的回调不应未经隔离直接并发。多份上下文快照合并需确定性，不能以任务完成顺序决定覆盖关系。

### 6.4 缓存范围与失效

| 可缓存候选 | 键或失效条件 | 禁止事项 |
| --- | --- | --- |
| 静态 Persona 和 Profile | Persona/资源版本 | 不同角色混用 |
| 能力摘要 | 配置、注册表、权限版本 | 撤权后继续曝光/执行 |
| 最近已确认历史摘要 | 会话与最后已提交 Turn 版本 | 包含未播放/未提交内容并称已发生 |
| 只读检索结果 | 用户/作用域、查询 revision、数据版本 | 跨用户命中或错用旧问题结果 |
| Provider 前缀缓存 | Provider 实际支持与返回证据 | 只因为前缀稳定就声称一定命中 |

对持续状态使用不可变快照/受控更新，不把任意变化全部写入永久缓存。失效代价、命中率、节省时间和一致性都要记录。

## 7. T6–T8 的范围与收益门槛

| 后续任务 | 开始前必须回答 | 暂缓条件 |
| --- | --- | --- |
| 动作小记录 | Provider 能否稳定输出合法小记录？消费者能否独立执行一条？ | 只是把旧 JSON 分块拼接，没有增量提交收益 |
| 本地动作编译 | 高频意图是否已有 Profile/ModelEngine 映射？如何避免参数冲突？ | 需要另建人格决策或未经授权改动角色语义 |
| ASR 期间预取 | 临时转写修订率、检索成本、取消能力怎样？ | 预取占满前台资源，收益低于额外请求成本 |
| 工具事实片段表达 | 哪些事实已确认？失败时如何保留不误导的前缀？ | 只能拿到未经验证 stdout 或输出可被整体推翻 |
| 连续 TTS 跨语义段 | 是否有可靠文本/采样映射和取消边界？ | 只能按字符数猜测音频归属 |
| AudioWorklet | 现有调度/主线程抖动是否导致实际欠载？ | 当前瓶颈在 Provider/入口，播放器替换无实测收益 |

本地动作并非一定等 T3 全部完成才可设计，但修订和融合必须有正式协议支持；不要为了并行推进留下无法接通的 producer。T6–T8 各自都要形成独立可交付切片，不合并成一次跨几十个文件的大重写。

```json
  "selected_mode": "M2",
  "process_instance_id": "...",
  "clock_domain": "renderer-instance-or-server-process",
  "event_monotonic_ms": 123.0,
  "event_epoch_ms": 456.0,
  "recorded_epoch_ms": 457.0
}
```

事件时间在发生处采集，recorded 时间只说明写日志时点。不要像现有 capture 事件一样，把早期 monotonic 与晚期 epoch 当成同一时刻。单次链路记录首事件即可，禁止按每个 token 打大段内容日志。

至少计算：

- 用户体验首声：同 renderer 的 capture-stop → 首采样；包含输入发送前等待。
- 服务响应首声：final 输入提交/ASR final → 首采样，明确跨进程校时条件。
- 首文本：输入确认 → 首个安全可见 delta，不能拿模型首 chunk 代替。
- 后端首交付：Core start → 首段物理发送；这是现有指标的一种，不是声音。
- 动作：意图就绪 → 首个合法 payload → 实际 sink 开始，各自记录。
- 连续性：欠载次数/时长、段间额外空隙、取消到静音耗时。
- 成本：额外请求、未使用预取、连接数、缓存量、内存峰值和失败率。

不要将存在重叠的 persona_ms、provider_ms、tts_ms 简单相加。用事件时间线判断关键路径。

## 9. 对照实验和性能回归保护

### 9.1 两类测量分开做

**固定下游材料：**使用同一份已确认文本、分段和动作意图，比较 TTS/传输/播放，减少模型输出长度差异。可用真实 Provider，但结果只能说明下游改善。

**真实用户输入：**固定模型、音色、Persona、上下文、截图设置和输入集，记录自然输出差异，比较完整体验。轮换 M0/M2 的运行顺序，分别标注冷/热启动，不让后一轮总享有预热优势。

M1 若只因 fallback 出现，标记 fallback 样本；不能计入 M2 成功数据。性能样本中音频成功但动作全失败，也不能当成与完整动作成功的 M0 同质量对照。

### 9.2 逐批验收门槛

- 正确性：相关场景没有挂起、重复播放、身份污染、未授权 TTS 或无法结束的动作；失败诚实收口。
- 模式真实性：至少一条真实入口 trace 证明选择并使用了 M2，而非降级后成功。
- 短回复保护：与 M0 同条件比较，不允许无解释的可重复首响/失败率回退；样本不足先标 unverified。
- 长回复收益：首声先于完整 Persona/音频 EOF，后续播放连续，动作无明显延后；是否比 M0 更快由数据决定。
- 资源：负载和慢播放下缓冲上限有效，控制响应不随队列积压无限增长。

前两项优先于收益。数值门槛在可信基线后提出，不在没有数据时硬写“必须低于三秒”。一个单次快样本不足以关闭任务，单次慢样本也不足以要求全面重构。

### 9.3 自动检查范围

选用现有 Python/Ruff/TypeScript 工具。先确认 pyproject、frontend/package.json 与依赖可用，再运行变更相关检查；不安装/升级无关环境来追求全绿。

每个有必要验证的公开边界通常一个成功输入和一个主要拒绝/取消输入即可。长回复失败队列和真实入口身份是当前必要边界，不可用只测私有函数取代。完整现场矩阵可逐批人工采集，不能补一堆 fake Provider 测试后写 live_verified。

## 11. 常见误解与禁止替代方案

| 容易误解 | 应采取的解释 |
| --- | --- |
| ordinary 模式快，所以不用修流式身份/取消 | 正确性独立于速度；保留普通模式，修复新路径再评估收益 |
| 真流式必须每个字都触发 TTS/动作模型 | Provider 可连续接受文本，但请求/动作提交应有合法边界和成本上限 |
| 动作失败是可选，所以全部取消也算优化完成 | 动作成功率和效果是用户目标，不可拿取消代替流水线 |
| 第一个 Provider chunk 已到，所以首响达标 | 还要经过文本提交、TTS、网络、播放器首采样 |
| 队列扩到几千条就解决了背压 | 只是延后溢出和增加内存/取消延迟 |
| 用 await gather 就自动消除串行依赖 | 先验证依赖、共享状态和副作用，再并行 |
| 预取结果晚到后放进 event 就影响当前模型 | 已发请求不自动接收新 prompt，须下一次明确调用 |
| 删除流式校验即可修 writer 绑定 | 会允许旧 Turn 写新连接；必须修生产者/绑定时点 |
| 给纯动作段塞静音音频触发 audio.started | 伪造媒体依赖；使用独立动作时间线 |
| 把成功 M0 改成默认 M2 就能验收 | 用户设置、能力、协议和真实质量必须分别确认 |
| 几次样本就能宣布 p95 稳定改善 | 保留样本数、冷/热条件和失败；低样本仅探索性 |
| 任务书越详细就越应该全量照做 | 细节用于减少误解；高风险任务仍受依赖和收益门槛限制 |
