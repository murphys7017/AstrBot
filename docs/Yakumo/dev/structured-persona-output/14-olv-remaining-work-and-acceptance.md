## 2. 下一步优先级

1. **P1：配套版本的真实 M2 验收。**先证实新链路确实在运行，再判定瓶颈；不得用请求设置 stream=True 或 M1 回退结果代替。
2. **P1：补齐性能与身体表现证据。**与上一步共同采集，避免先做更多高风险架构改造而缺少可比较基线。
3. **P2：定位历史 M0 首段动作异常。**使用新终态观测复现，不根据缺少 started 推断具体根因。
4. **P2：T6 动作小记录。**真实样本确认 EOF 等待的代价后，先确定完整契约，再分批实现。
5. **证据触发的候选项。**额外连接准备、段头协议负担、AudioWorklet、跨段连续 TTS 等，只有当前瓶颈和收益依据成立时才推进。

以上是执行顺序，不是所有候选技术必须全部落地的承诺。保留用户已观察到的 M0 短回复约三秒体验，不自动强制切换模式。

## 3. P1：真实 M2 验收步骤与退出条件

### 3.1 先确认运行前提

- 重新读取两个仓库指南、HEAD、相关工作区差异及当前日志；历史模式/进程状态不能直接沿用。
- 区分源码、部署副本和实际加载进程。无法证明的运行版本标为 unknown，不补写为一致。
- 新协议要求配套 Adapter 和桌面：server manifest 包含 `audio_credit=olv.audio_credit.v1`，桌面 runtime settings 发送相同的 `audio_credit_schema`，Adapter 本连接协商成功。Core 同时加载配套身份、producer 与生命周期实现。
- 如果需重启、切模式或真实 Provider 调用，先核对当前会话授权与用户正在进行的对话；本次更新文档本身不执行这些操作。逐项提交授权继续有效。
- 固定并记录 Provider/模型/音色、上下文条件、截图设置、设备和冷/热状态。日志仅保存必要身份、阶段、数量和错误，不复制完整私密对话。

### 3.2 最小现场场景

| 场景 | 必须看到的事实 | 失败时优先调查 |
| --- | --- | --- |
| 冷、热短回复 | writer 准入；实际 text/PCM 增量；首采样早于整轮生成结束；文本/声音各一次 | 模式回退、准备耗时、首文本/首 PCM 等待 |
| 两至三段 | 首段在后续生成期间播放；段间音频与动作交接合理；排空后单次回执 | 前段 drain、motion blocker、段 flush 和归属 |
| 长回复及慢消费 | 容量有界，字幕/控制/动作不因慢播放停滞；信用持续归还；不挂起/静默丢帧 | 信用等待、worker、设备缓冲、生产/消费终态 |
| 首 PCM 前及播放中打断 | 当前任务/信用等待退出，设备停播；连接未因正常本地取消误判失败；新 Turn 无旧采样/动作 | 代次、迭代器关闭、取消与服务端 echo 竞态 |
| 断连后重连 | 旧 writer/worker 失效，新连接重新协商；旧事件不重放 | 连接所有权与 credit 重建 |
| 动作慢、纯动作及可选失败 | 音频不等待动作；无音频可结算；迟到/失败有明确终态，无过期补播 | 生产 deadline、身体准入、窗口与终态 |

现场无法安全触发的故障保留“未验收”，不要通过破坏用户配置制造故障；已有边界验证可作为补充证据，不能替代硬件场景。

### 3.3 记录与完成判定

每次请求关联 frontend Turn、Core Turn、Persona result、segment/message 和构建身份。分别记录输入确认、首有效文本、首 PCM、软件首采样估计、首动作启动、生产结束、播放排空及 Turn 终态；失败样本也必须保留。

`pcm_first_sample.monotonicMs` 是软件消费估计；估计 epoch 为同一 renderer 的 `timeOriginMs + monotonicMs`，`timestampEpochMs` 是回调记录时刻。进程内耗时用同一时钟域相减，跨进程时钟未校准时注明误差；均不得声称硬件出声实测。

先取得可解释的成功样本，再在资源允许时采集约 20 次可比请求；样本不足就报真实数量/范围，不包装成稳定 p95。M0/M2 比较应控制输入、输出长度、配置、上下文和冷/热状态，记录失败率、段间间隙/欠载与资源峰值。已观察到的 M0 约 3.26–5.07 秒历史六样本不是 M2 性能结果，也不是同条件 A/B。

本项完成需要配套运行版本证据、实际 M2 文本/PCM/播放/动作记录、现场场景结果与明确残余缺口。没有数据时不写速度提升百分比；任何失败先按真实错误修复并单独提交，不重新实现已经通过边界的整条链路。

## 4. P2：动作连续性与历史 M0 异常

真实 M2 需观察后到动作是否在当前语音窗口执行、下一段能否自然交接、默认 speech-only 是否抢占、动作失败是否正确释放结算。模型 app 的 motion-stream-open 准入修正只有源码/类型验证，不能据此宣布视觉问题全部解决。

历史 M0 样本：frontend Turn `input:34f88a10fa7a419ea11243f7a2813b21`，Core Turn `a88ec1efd14e4676ab909926e8d180ae`。03:12 首段有 `motion_ended` 无 `motion_started`，后段有实际 started/completed。旧 ended 可能代表失败或中断；现已拆分 `motion_ended`、`motion_failed`、`motion_interrupted`，但尚未复现并定位当时根因。

下一步将新日志中的 motion 请求、校验/拒绝原因、身体准入和终态串联；不能把 M2 的 speech-only 修正当作历史 M0 根因修复。完成条件是明确的复现/根因/修复证据，或明确记为历史不可复现并保留缺口。

**新增可定位样本及修正：**15:39–15:42 五轮 M0 均复现首段动作生成成功、桌面以 `motion_plan_not_prepared_before_audio_start` 拒绝；第二段成功。根因是后到动作缺少 ModelEngine 准备流程，修正已补已知时长窗口内的编译与接入采样时钟归零，真实 ModelEngine 公共边界和完整构建通过。细节见 [10 第 9 节](10-olv-runtime-evidence-2026-10-17.md#9-15391542-新-m0-样本首段后到动作准备失败)。随后 M2 未知时长准备也已追加修正，见第 10 节证据。接下来需确认实际加载版本，复测首段左右动作、未知总长 PCM、打断及段间交接；不追认 03:12 旧样本的具体根因。

## 5. P2：T6 动作小记录实施前必须补齐的契约

当前 `motion/text_stream.py` 仍累计到 EOF，`middleware/interaction_motion/independent.py` 随后解析完整 JSON；当前 prompt 要求单个完整根对象。桌面也不会以新 payload 替换已释放/本地结算的动作。仅打开 Provider 流式或截取第一对花括号不能解决此问题。

实施前先形成可审阅切片：

1. 定义闭合小记录及失败语义：Turn/段身份、顺序/revision、操作、合法模型资源/参数、有效窗口、结束标记和最终聚合规则。`anchor`/revision 目前是待设计字段，不是现成 API。
2. 同步 producer prompt、增量 parser、校验和协议协商。完整合法记录才可提交，半截 JSON 不执行；后续错误保留已接受前缀并显式失败。
3. 接通实际 PlaybackTimeline/ModelEngine：明确本地预览与云端动作的参数所有权、替换/叠加、音频采样锚点、迟到拒绝、打断回收和去重；不能绕过 Profile 校验直接操作模型参数。
4. 保留最终聚合审计，避免已执行记录在最终结果再次播放。每批完成可审阅行为与必要公共边界验证后提交；协议变更同时准备两端。
5. 用真实动作 Provider 和 Live2D 证明首条合法动作在 EOF 前执行，重复/坏记录不造成重播或跨 Turn 污染；同时记录实际提前量和视觉质量。

若真实 Provider 不能稳定输出所需记录，先保留证据并调整契约；不要增加另一个通用 Persona 或隐式回退来掩盖失败。
